# Borrow Next Door 项目方案与四人分工

赛事：AdaHack 2026  
赛题：People’s Postcode Lottery — Greener by Postcode  
团队规模：4 人  
提交截止：2026 年 10 月 3 日 18:15，英国当地时间  
文档性质：基于赛题材料制定的实施建议；功能、工期和分工为团队计划，不代表官方评分细则的进一步解释。

## 1. 项目定位

**帮助邻居借用闲置工具，一起完成社区绿化和环境维护行动。**

项目介绍：

> Borrow Next Door helps neighbours turn unused tools into shared action for a greener postcode.

居民输入邮编，查看附近绿地和社区工具，选择想完成的环保任务。系统根据任务列出所需工具，匹配附近可借物品，并支持申请、确认借出和归还。

核心亮点是“按任务凑齐工具”：新加入的邻居提供一件工具，就可能让原本无法开展的行动具备条件。这直接回应赛题中“参与邻居越多，产品越有用”的加分目标。

### 核心演示故事

1. Alice 想清理附近绿地，但缺少垃圾夹。
2. Alice 输入邮编，选择绿地和“清理绿地”任务。
3. 系统展示所需工具，标记垃圾夹暂缺。
4. 邻居 Bob 发布一把可借垃圾夹，Alice 的页面出现匹配结果。
5. Alice 发起申请，Bob 接受，任务所需工具得到确认。
6. 工具实际交接后，Bob 标记借出。
7. 活动结束，Bob 确认收到归还工具，工具重新可借；Alice 提交任务成果。

**必须区分：发现可借工具、预约得到确认、实际借出、任务完成。这四件事分别记录。**

## 3. 最小可交付版本

### 必做功能

- 邮编输入和社区位置识别。
- 附近绿地展示；地图来不及时先展示名称及位置列表。
- 工具列表：类别、出借者昵称、所属社区、可用状态。
- 发布工具：名称、类别、简短描述、位置关联。
- 两个固定任务模板：清理绿地、照顾社区花坛。
- 工具清单和匹配结果，显示尚未落实的物品。
- 申请、接受或拒绝、交接借出、确认归还。
- 两位演示用户访问同一份共享数据。
- 社区首页的区域空气、电力信息卡；接口失败时显示不可用或带时间的缓存。
- 任务完成记录和真实来自应用记录的成果统计。
- 首页 hero 与环境卡之间的 “Stories from the street”：轮换展示本街区最近记录的行动（发起人 + 自报成果 + 行动名/日期），数据直接来自共享任务记录，不另存一份；种子数据在两个街区各自预置 2 条。

### 有余力再做

- 任务照片、工具照片上传。
- 缺少工具需求板。
- 任务完成后的数字花园或街道动画。
- 距离排序和更多任务模板。
- 参与者自报的“如果借不到，是否会购买新品”调查。

### 本次暂缓

即时聊天、支付和押金、信用评分、商业奖励、全国排行榜、AI 图片识别、自动估算产品全生命周期碳排放、复杂预约日历。

耗材涉及赠送而非归还，第一版以可重复使用工具为主。垃圾袋等耗材可以列为“自备”，不接入借还状态机。

## 4. 页面与交互

| 页面 | 主要内容 | 用户的关键操作 |
|---|---|---|
| 社区首页 | 邮编、区域环境卡、附近绿地、工具列表 | 输入邮编、筛选工具、开始一个任务、发布工具 |
| 任务详情 | 地点、工具需求、匹配结果、确认情况 | 选择工具、申请借用、标记自备物品、提交任务成果 |
| 我的借出与借入 | 待处理申请、预约、借出和归还记录 | 接受或拒绝申请、确认借出、确认归还 |

演示用户入口可以提供 Alice 与 Bob 两个测试账号，明确标注演示身份。两人必须使用共享后端数据；单一窗口的本地假数据不能证明多人流程已实现。

## 5. 四人分工

先用 A、B、C、D 代指成员，开工时填上姓名。

| 成员 | 姓名 | 主要角色 | 负责交付 | 与其他人的交接 |
|---|---|---|---|---|
| A | 待填 | 前端与整合负责人 | 页面框架、社区首页、工具列表和发布表单、我的借入借出页面、加载与错误提示、整体运行入口 | 消费 B 的工具与借用接口、C 的社区数据、D 的任务组件 |
| B | 待填 | 数据与借还流程负责人 | 数据表、演示身份、工具和请求接口、借还状态转换、共享数据持久化、重复预约防护 | 先交付统一数据结构和样例，再让 A、D 接入真实数据 |
| C | 待填 | 邮编与环境数据负责人 | 邮编定位、附近绿地、空气与电力数据、统一返回格式、时间和来源标注、缓存与失败降级 | 向 A 提供环境卡片数据，向 D 提供任务地点 |
| D | 待填 | 任务匹配与成果负责人 | 两种任务模板、工具清单组件、匹配规则、缺口与确认状态、任务完成记录、成果统计；汇总展示材料 | 从 B 读取工具和借用状态，使用 C 的绿地，向 A 提供可接入的任务模块 |

### A 的完成标准

- 三个主要页面可以连续操作，页面导航不打断流程。
- 空列表、加载中、接口失败都有清楚反馈。
- 按钮执行真实操作，操作成功或失败后显示结果。
- 与其他成员共同完成双窗口整合；负责统一可运行的演示入口。

### B 的完成标准

- 两个演示用户可以读取同一份工具和任务数据。
- 工具发布、申请、接受、拒绝、借出、归还均有持久记录。
- 服务端控制关键状态转换，不能仅靠前端隐藏按钮。
- 一件工具无法同时被两人成功预约。
- 第一轮整合前提供一套可重置的演示数据。

### C 的完成标准

- 有效邮编能返回位置；无效邮编有明确提示。
- 附近绿地、空气、电力各自独立加载，单个源失败不影响借还功能。
- 数据带来源、更新时间和范围说明。
- 查询结果为空时正常显示；演示缓存注明“缓存”和采集时间。
- 使用示例绿地时显式标注，避免与真实查询结果混淆。

### D 的完成标准

- 选择模板后自动生成工具需求清单。
- 依据类别、状态和社区位置匹配现有工具。
- 区分“有工具可申请”与“出借者已确认”。
- 借用完成不自动等于任务完成，任务成果单独提交。
- 工具清单（02）是可选项：没凑齐工具也能提交成果（03），清单只显示自己的进度。
- 汇总真实实现范围、演示脚本、团队贡献及已知限制。

每位成员都负责检查自己模块。D 统筹展示材料，但四人均需要提供自己的内容，避免把全部整理工作留到最后。

## 6. 开工前约定的接口和规则

前 30 分钟共同确认字段和职责；以下是建议结构，可以按熟悉的技术栈调整。

### 最小数据对象

| 对象 | 建议字段 |
|---|---|
| User | id、display_name、postcode、latitude、longitude |
| Tool | id、owner_id、name、category、description、status |
| LoanRequest | id、tool_id、borrower_id、task_id、status、created_at、returned_at |
| Task | id、creator_id、template_id、place_name、latitude、longitude、status、outcome_note |
| TaskRequirement | id、task_id、category、quantity、source_type、loan_request_id |
| EnvironmentSnapshot | location、air、electricity、green_spaces；每项带 source、timestamp、scope、status |

MVP 每类工具可以先只需要一件。工具位置通过出借者的社区位置获得，任务地点单独保存。

### 建议的借用状态

请求状态：`pending → accepted → on_loan → returned`；另设 `rejected` 和 `cancelled`。

工具状态：`available → reserved → on_loan → available`。

- 第一版允许每件工具同时只有一个待处理或有效请求，申请时暂时保留该工具。
- 拒绝或取消待处理请求时，工具恢复可借。
- 接受申请代表确认预约；实际交接后再标记借出。
- 归还由出借者确认后恢复可借。
- 服务端应原子地检查工具可用状态并创建预约，防止并发重复预约。
- MVP 工具清单标注“已落实”时，依据已接受的预约、已借出工具或用户确认自备；仅找到可借工具时标注“可申请”。

### 模块提供的能力

- B → A/D：列出工具、发布工具、创建请求、查询本人请求、执行状态转换、读取与保存任务。
- C → A/D：解析邮编、读取绿地和环境信息，统一处理来源状态。
- D → A：任务模板、任务清单组件、匹配结果和成果视图。
- A → 全员：页面入口、共享样式、统一身份状态和整合约定。

优先选择团队熟悉的技术栈，使用一个共享数据库。状态同步使用定时刷新或操作后刷新即可，不必把实时通信作为前置条件。

## 7. 环境数据及成果指标

| 功能 | 建议来源 | 产品中的用途与边界 |
|---|---|---|
| 邮编定位 | Postcodes.io | 定位社区；以邮编中心点估算附近范围时应注明近似位置 |
| 附近绿地 | OpenStreetMap Overpass | 查询已映射的绿地作为任务地点；不据此推断垃圾或维护需求 |
| 空气信息 | Open-Meteo Air Quality | 欧洲数据约为 11 km 网格预测，标注为区域预测 |
| 电力信息 | NESO Carbon Intensity API | 邮编对应区域的电力碳强度，标注为区域信息 |

邻里优先匹配同一邮编；如需扩大范围，可增加附近搜索。展示中心点直线距离时注明“约”和“直线距离”，不要称为步行路程。

外部 API 的实时连通性需要 C 在开工时确认。此前已核对官方文档，但这不等于本机、本网络上的接口已全部实测。

### 成果面板

- 完成借用次数：来源为状态为 `returned` 的借用记录。
- 工具得到确认的任务数：来源为所需工具预约确认或自备确认记录。
- 完成社区行动数：来源为任务完成记录，明确为发起者提交。
- 清理袋数、参与时长：B 契约里是可选的 `outcome.bags_collected` / `outcome.volunteer_minutes`，但 03 面板已不提供输入（2026-10-03 决定），因此面板上这两项在没有数据时显示未采集，不报 0。
- 潜在避免购买次数：仅在加入对应问卷后展示，注明为用户自报。

不同指标分别计数。同一把工具的多次借用不能直接当成减少了同等数量的新工具生产。空气预测和区域电力变化也不能被当作本项目行动的实测成果。

## 8. 开发节奏与整合节点

按约 7–8 小时可用时间安排。现场时间不足时优先保留完整借还流程和任务匹配，压缩可选功能。以下相对时间不是官方赛程。

| 阶段 | A | B | C | D | 共同验收点 |
|---|---|---|---|---|---|
| 0–0.5 小时 | 页面草图、公共样式 | 数据和状态约定 | 检查数据源与演示邮编 | 定义任务模板和演示故事 | 确定工具类别、字段、身份、接口 |
| 0.5–2 小时 | 页面框架和工具列表 | 发布与读取工具、演示用户 | 邮编定位、绿地和环境数据适配 | 工具需求清单与匹配逻辑 | 第一位用户发布后，第二位用户能读到 |
| 2–4 小时 | 借用页面与操作反馈 | 请求、接受、借出、归还 | 来源标注、缓存、错误处理 | 接入真实工具和请求状态 | 双窗口跑通一次借还流程 |
| 4–5.5 小时 | 整体页面整合 | 状态一致性与冲突修复 | 支持演示地点、处理空结果 | 完成成果记录与统计 | 从邮编到任务完成的完整演示 |
| 后续时间 | 界面与运行入口 | 修复阻断问题 | 数据稳定性与说明 | 汇总展示材料 | 全员检查和演练 |

| 时间 | 成员 | 讲述或操作 |
